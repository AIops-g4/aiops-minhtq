Detection chạy 2 nhánh rồi merge về cùng schema

Metric anomaly và log template anomaly khác cách tính, nhưng đều emit EvidenceCandidate để stage sau xử lý thống nhất.

Metric branch

Tách service.metric, chia baseline/post-alert, tính delta, ratio, slope, z-score rồi emit metric evidence.

Log branch

Normalize raw message thành template, group theo svc + level + template, tính severity, burst, keyword và metric-link score.

Why merge?

Correlation/RCA không cần đọc raw data. Chúng dùng chung service, timestamp, score, signals, evidence_id.

05 - Detection logicMetric + log branches

Feature 001 / Variables For Score

Score được tạo từ biến metric và biến log

Slide này là phần “nguyên liệu”: metric branch tạo anomaly signals, log branch tạo các score thành phần. Slide sau mới biến chúng thành score.

Metric variables

directional_zZ-score theo hướng metric xấu đi, ví dụ latency tăng hoặc availability giảm.
robust_z(end - median) / (1.4826 * MAD), ít nhạy với outlier baseline.
driftabs(post_mean - baseline_mean) / baseline_std, bắt dịch chuyển sau alert.
ratioend_value / baseline_mean, bắt mức tăng/giảm tương đối.
slope_signalabs(slope) / abs(baseline_mean), bắt tốc độ degrade kéo dài.

Log variables

severity_scoreERROR = 1.0, WARN = 0.6, INFO = 0.2.
frequency_scoreTăng khi cùng template xuất hiện nhiều lần trong incident.
burst_scoreTăng khi log dồn dập trong một khoảng thời gian ngắn.
keyword_scoreBắt keyword vận hành như timeout, pool exhausted, DNS, TLS, OOM.
metric_link_score1.0 nếu service có log anomaly đồng thời có metric anomaly.
template = "ConnectionPool timeout ..."
level    = ERROR
count    = 84
keyword  = timeout + pool
metric_link_score = 1.0
06 - Score variablesMetric + log ingredients

Feature 001 / Score Computation

score là suspiciousness của evidence

Feature 002 filter bằng min_score, nên Feature 001 phải biến metric/log bất thường thành score chuẩn hóa trong [0, 1].

Metric score

raw_score = max(
  abs(directional_z) / 8,
  abs(robust_z) / 10,
  drift / 6,
  abs(ratio - 1) / 2.5,
  slope_signal * 20
)
score = clamp01(raw_score + bonus)

Dùng max(...) vì metric có thể bất thường theo spike, drift, ratio hoặc robust z-score. Operational metrics như latency, error rate, memory, pool được bonus nhỏ.

Log score

log_score =
  0.25 * severity_score +
  0.20 * frequency_score +
  0.20 * burst_score +
  0.25 * keyword_score +
  0.10 * metric_link_score

Dùng weighted sum vì log đáng nghi khi vừa nghiêm trọng, vừa lặp nhiều, vừa burst, có keyword vận hành và trùng service có metric anomaly.

Metric signals

metric_increase/decrease từ hướng delta; anomaly type từ tên metric như latency, error, memory, pool, dns; sau đó thêm metric_spike và post_alert.

Log signals

Luôn có log_template và log_level_*; keyword trong template sinh pool_anomaly, timeout_anomaly, dns_anomaly, tls_anomaly; metric match thêm metric_linked.

Score này không phải confidence của action. Nó chỉ trả lời: evidence này đáng nghi đến mức nào để giữ lại cho correlation/RCA?

service + time range

Giữ trace từ final decision về raw incident path. Một evidence được assign vào đúng một cluster.

details

Metric details chứa baseline/delta/z-score; log details chứa template_id, count, raw examples. Đây là phần debug và retrieval fingerprint.

09 - Feature 002Alert clusters

Feature 002 / Logic

Time session trước, topology grouping sau

Step 1

Filter

Giữ evidence có score >= min_score. Default 0.28 để không drop evidence detection đã coi là hữu ích.

Step 2

Session

Group theo detected_at. Alert liên tiếp cách nhau không quá gap_sec = 300 thì cùng burst.

Step 3

Topology + traces

Merge service nếu shortest path <= max_hop = 2, có augment bằng live traces.

Trace augmentation quan trọng vì một số runtime service có thể không có trong static topology nhưng vẫn xuất hiện trong metrics/logs/traces.

13 - Feature 003Culprit ranking

Feature 003 / Rankers

Không tin một heuristic duy nhất

Weight 0.40

PageRank

Chạy trên graph caller -> callee. Downstream dependency thường là nơi lỗi gốc lan ngược lên caller.

Weight 0.35

Timestamp

Tìm service degrade sớm nhất bằng metric z-score; fallback về earliest evidence timestamp.

Weight 0.25

Causal-lag

Dùng cross-correlation giữa anomaly series để xem service nào lead service khác.

Nếu thiếu data cho một ranker, output vẫn ghi warnings để decision layer xử lý bảo thủ hơn.
14 - RCA rankersGraph + time + lag

Feature 003 / Fusion

RRF hợp nhất bằng thứ hạng, không cộng raw score

Reciprocal Rank Fusion

rrf_score(service) =
  sum(weight_m * 1 / (rrf_k + rank_m))

rrf_k = 60 làm mượt để ranking ổn định khi ranker có scale khác nhau.

Confidence gap

(score_top1 - score_top2) / score_top1. Gap thấp nghĩa là culprit candidates quá sát nhau, decision nên giảm confidence hoặc escalate.

16 - Feature 004Decision layer

Feature 004 / RAG-style Retrieval

History corpus hiện tại là incidents_history.json

Đây là hybrid retrieval trên structured history, chưa phải vector DB đầy đủ. Top neighbors được đưa vào action voting và LLM prompt.

Retrieve by overlap

affected_services, log_signatures, trace_signatures, metric_signatures.

Vote by outcome

vote = similarity * outcome_weight. Success mạnh hơn partial, failed gần như không được ưu tiên.

Action catalog

actions.yaml giới hạn action hợp lệ, required params, cost, downtime và blast radius.

Safety Guardrails

LLM được dùng có kiểm soát

LLM giúp summarize/classify, nhưng decision phải pass validation và safety checks.

RCA boundary

root_cause_service phải nằm trong RCA candidates.

Action schema

selected_action phải tồn tại trong actions.yaml và đủ params.

Fallback

LLM off, missing key, invalid JSON hoặc conflict thì dùng deterministic fallback.

Escalation

Evidence mới/yếu/conflict thì chọn page_oncall thay vì đoán.

Guardrails giữ hệ thống an toàn khi LLM trả JSON sai, chọn action không hợp lệ hoặc evidence chưa đủ mạnh.
